# Migrations

Rules (ODZ - Development SOP 5.2, Playbook section 4):

1. Every migration is a local SQL file in this folder **before** it is applied anywhere.
2. RLS is enabled on every table, with policies, from the migration that creates it. No table ships without policies.
3. No dashboard-only changes. If it is not in a file here, it does not exist.

Name files `YYYYMMDDHHMMSS_short_description.sql`.

The repo is public: no member data in migrations, seeds or fixtures. Obviously fake data only.

## Applying

Apply files in filename order to the ODZ Supabase project (SQL editor or `supabase db push`). If you apply through the dashboard or an MCP tool that stamps its own timestamp, rename the local file to match the recorded version so history stays in sync.

## Current schema (MVA-198)

`20261010181521_db_foundation.sql`: `tiers`, `capabilities`, `tier_capabilities`, `profiles`, the signup trigger, `has_capability()`, RLS on all four tables, and the first seed.

`20261010181757_tier_model_and_audit.sql`: Dax decisions of 2026-10-09 and 10-10. Ladder is Command > Old Guard > Member > Contractor > Prospect > Recruit (Admin is the `is_admin` flag, not a tier); lower `rank` means more authority. Command requires Old Guard to enter and releases back to Old Guard, stored as data on the tier (`entry_requires_tier_id`, `release_to_tier_id`). New `edit_roster` capability (Command by default) governs tier changes; `approve_members` governs status, and may assign the tier when approving a pending account. `profile_audit` records who changed status, tier or admin and when (append-only, written by trigger, readable by approvers and roster editors). Recruit is the default tier on approval.

`20261011121739_invites_and_private_data.sql` (MVA-199, applied 2026-10-11): invite-only signup, first-login setup, private member data.
* `invites` (server-generated 20-char code, tier Recruit/Prospect/Contractor, 7-day expiry, single use, revocable) with `invite_audit`. Command/Admin (`approve_members`) issue, read and revoke; nobody else can read them.
* Signup is gated in the database: `handle_new_user()` consumes the code from the signup metadata (`invite_code`) via `redeem_invite()`, so a direct Auth API call without a valid code fails. Side effect: users cannot be created from the dashboard without an invite either (make one with `supabase/seed/first_invite.sql`).
* `check_invite(code)` is the only anon-callable function. It returns true/false, never says why, and locks a source out for 15 minutes after 5 bad guesses (50 overall). It identifies the source from `cf-connecting-ip`, then `x-real-ip`, then the first `x-forwarded-for` entry; verify on the live project that one of these is set by Supabase's proxy.
* `member_private` (legal name, date of birth, phone, allergies, emergency contact): owner reads/writes own row; `view_member_private` (Command) reads all; only admins delete. Writes are logged in `profile_audit` (event `private`) by field name only. `complete_setup()` validates and writes it atomically and sets `profiles.setup_complete`; its errors are fixed codes that never echo values.
* `20261011130000_remove_bootstrap_admin.sql`: signup is invite-only for every address. The initial admin was created by hand in the Supabase dashboard (a dashboard-added user needs an invite code in its metadata too; see that file).
* `approve_member()` / `reject_member()` (need `approve_members`; approval requires completed setup and keeps the invited tier).

`20261011140000_admin_settings.sql` (MVA-141): invite codes become show-once (`create_invite()` returns the code; only `code_hint`, the last 4 characters, is readable afterwards; direct inserts closed). `list_invites()`, `list_audit()` (profile, invite and settings events, field names only for private data), `my_capabilities()`. Tiers and capabilities change only through admin RPCs (`create_tier`, `rename_tier`, `reorder_tiers`, `delete_tier`, `set_tier_capability`); direct writes revoked. Guards: Command entry/release rules cannot be changed, a tier with members cannot be deleted, `approve_members` cannot be removed from every tier, `view_member_private` changes need the typed word `PRIVATE`, nobody changes their own tier. `tiers.invitable` replaces the name check for which tiers an invite may grant. New `settings_audit` table.

`20261011150000_events.sql` (MVA-201): `events` (RLS: read needs `read_event_details`, write needs `write_events`; no client can set `created_by` or `external_id`), the `public_events` view (title, type, times, status only; the only thing anon can read), audit rows in `settings_audit` (titles only). `read_event_details` is removed from Recruit, Prospect and Contractor (Member and above keep it; Admin can toggle it).

`20261011160000_profiles_directory.sql` (MVA-204): `profiles.role_note` (<=60), `bio` (<=280), `joined_at` (first approval; backfilled). Members edit only display name, role note and bio through `update_own_profile()`; direct updates of profiles are closed except tier, status and is_admin for roster managers (the own-row update policy is gone). `set_callsign()` (edit_roster) and `update_own_private()` added; profile edits are audited by field name only.

`20261011170000_minutes_documents.sql` (MVA-202): `minutes`, `minutes_files`, `documents` with RLS; private `minutes` storage bucket (10 MB cap, extension whitelist, path-shape and write_minutes policies on `storage.objects`; created only where the storage schema exists). New capabilities `read_documents` (Member and above) and `publish_documents` (Command); `read_minutes` removed from Recruit, Prospect and Contractor. One ratified version per slug (DB index; ratifying supersedes the old one). Content sniffing by magic bytes happens in the app before upload. Nothing is seeded.

`20261011180000_hq_panels.sql` (MVA-142): `write_traffic` (Command), `traffic` (archive only, titles-only audit), `event_rsvps` (own row, only before an event starts, never for a cancelled one), `event_readiness()` and `tier_breakdown()` (counts only). `tiers.counts_for_readiness` marks which tiers count toward readiness (Command, Old Guard, Member; Contractor is excluded because it cannot RSVP); it is data on the tier, not edited from the admin screen yet.

`20261013190000_member_removal.sql` (MVA-209): soft removal and hard delete, both Admin-only SECURITY DEFINER RPCs.
* `profiles.status` gains `removed`; `removed_at` and `removed_by` added (additive, no row rewritten). `remove_member(profile, reason)` marks the profile, purges `member_private`, notifications, prefs and push subscriptions, revokes the member's unused invites, bans the auth user for 100 years and ends their sessions. The tier and callsign are kept (history and seniority are not touched). Refuses: non-Admin, self, the last Admin, an already-removed member, a reason outside 3 to 500 characters.
* `delete_removed_member(profile, reason)` hard-deletes a removed member (auth user, cascading to the profile, RSVPs and private rows). Authored events, minutes, documents and traffic stay with a null author, shown as "Former member".
* `member_removals`: Admin-only log (who, whom, when, reason, callsign snapshot, no FK so it outlives the profile). The reason lives here and not on `profiles`, because other members and the removed member can read profile rows. `list_audit()` includes these rows for Admin only.
* `profiles_guard()`: `removed` can only be set by `remove_member()`; a removed row is frozen for signed-in callers (no reinstating, no tier change). `member_private` refuses writes for a removed account (covers setup of an account removed before it finished).
* The `created_by` before-update triggers on `events`, `minutes`, `documents` and `traffic` pinned the author, which made the foreign keys' ON DELETE SET NULL fail. They now allow created_by to become null when the author no longer exists.
* Re-onboarding: a removed account stays banned and keeps its email and callsign. Someone who returns needs a fresh invite and either a different email and callsign, or the Admin hard-deletes the removed account first.

`20261013220000_support_tier.sql` (MVA-237): the Support tier, a role-based tier for non-playing team members.
* `tiers.role_based` marks Support (data, not a name check); `tiers.support_barred` marks Command and Old Guard, which can never be moved to or from a role-based tier. Support is last in the list for display, is invitable, does not count for readiness, and has **no capabilities**. Traffic is readable by any approved account, so Support reads it without a grant; event details, minutes, documents, RSVPs and `member_private` stay behind their capabilities.
* `move_support_tier(profile, tier, note)` (edit_roster; note 3 to 300 characters) is the only way across the player/Support line; `profiles_guard()` refuses direct updates that cross it for signed-in callers. The note is stored on `profile_audit.note` (new column) and shown in the Audit feed. Moving a Support account into a player tier that has no private details re-opens first-login setup, so they are collected first. Private details of a player moved to Support are kept.
* `complete_support_setup(callsign)` and `my_tier_is_role_based()`: Support's first-login setup asks for a callsign only.
* `invites_prepare()`: an invite with no tier still defaults to the least senior **player** tier (Recruit).
* Office-seat rejection for Support (designations) is built in MVA-220, which reads `tiers.role_based`.

`20261014020000_seat_caps.sql` (MVA-234): Old Guard and Command seat caps, enforced in the database.
* `seat_caps` (one row, 12 and 3): `old_guard_max` counts Old Guard and Command together (Command is part of Old Guard), `command_max` counts Command. Only an Admin changes them, through `set_seat_caps()`, logged in `settings_audit` (who, old, new); a change applies to future moves only. Any approved account may read the row.
* `tiers.seat_group` (`old_guard` / `command`) says which tiers hold seats, so renaming a tier never breaks the rule. This migration sets it on the two existing tier rows (the only existing rows it touches; no member data).
* `profiles_seat_cap()`: before insert/update trigger on `profiles` (fires after `profiles_guard`, so the Command release rule has already rewritten the target tier). Only a transition into a seat is checked, with one advisory lock so simultaneous promotions cannot both pass the cap. Errors read "Old Guard is full: 12/12" and "Command is full: 3/3". Approved and suspended accounts hold a seat; pending, removed (MVA-209) and deleted accounts do not, so removal and demotion free a seat at once. Covers roster edits, approvals, the SQL editor and bulk updates.
* `seat_counts()`: counters for the roster page; seat holders, roster managers (`edit_roster`, `approve_members`) and Admin only.
* Deploy check: if a tally is already over a cap the migration still applies (nothing is moved), writes a `seat_caps_over` row to `settings_audit` and prints a notice; promotion stays blocked until the count is under the cap.
* Invites cannot carry Old Guard or Command (those tiers are not `invitable`; unchanged, now tested).
* No function from an earlier migration is redefined.

`20261102180000_designations.sql` (MVA-220): duty roles (Treasurer, Quartermaster, Shop Manager, XO, Training Officer) layered on top of the rank ladder and the Admin flag.
* `designations` is the catalog (name, description, the one capability it grants, `office_seat`, `max_holders`); migration-managed, no client write. `member_designations` is the live assignment table (RPC-written only). `designation_audit` logs every assign/revoke (who, whom, designation, when); no FK on `profile_id`, same reasoning as `member_removals`.
* `office_seat = true` (Treasurer, Quartermaster, XO, Training Officer) is eligible to Command and Old Guard only, reusing `tiers.seat_group` (MVA-234), not a name check; one person may hold more than one seat. Shop Manager (`office_seat = false`) is open to any tier, Support (MVA-237) included. Eligibility and the holder cap are enforced in `assign_designation()`, not only offered by the UI.
* `has_capability()` and `my_capabilities()` (redefined) union in a profile's own designation-granted capabilities, plus every designation capability for Command automatically (`tiers.seat_group = 'command'`, Dax ruling 2026-10-13) with no assignment needed. Both read live rows, so a rank demotion or a revoke removes a capability on the next check.
* `assign_designation()` / `revoke_designation()` need `edit_roster` (Command by default, Admin passes every check), the same gate as other roster-editing actions. `designation_holders(id)` is the cross-app "list active holders" helper (excludes soft-removed members). `designations_overview()` backs the Vacant list, visible to Admin, `edit_roster` holders, or any seat holder (Old Guard or Command) — the same three-way check as `seat_counts()`.
* `list_audit()` (redefined) picks up a `designation_audit` branch, visible to the same audience as the rest of the feed.
* Seed: five capabilities (`manage_treasury`, `manage_inventory`, `manage_shop`, `hold_office_xo`, `hold_office_training` — the last two are placeholders from Lord's amendment on the run order, grant no powers yet) and the five designation rows. Adding one later needs no schema change beyond a new seed row and capability.
`20261102210000_service_history.sql` (MVA-210): member service history and prior missions (archive + seniority display).
* `service_records` (one row per profile: `doe`) and `service_history` (entries: date, title, location, role, notes, `source` = `app`/`manual`) are their own tables, not columns on `profiles`, so RLS can gate them more narrowly than the roster-wide profile fields (same reasoning as `member_private`).
* `can_view_service_record(profile)`: the owner, Admin, `edit_roster` holders, or any seat holder (Old Guard or Command) -- the same three-way check as `seat_counts()` and `designations_overview()`, plus the owner. Writes (`set_doe()`, `add_service_entry()`, `update_service_entry()`, `delete_service_entry()`) need `edit_roster`.
* Seniority is a display metric only (Dax ruling, 2026-10-13): no computed rank, no tie-break logic. DOE, years of service and mission count are shown for a human on Old Guard/Command to compare; a missing DOE is flagged in the UI, not computed around. Mission count is `count(*)` on `service_history`, so manual/archive entries and any future app-recorded attendance (`source = 'app'`) both count without extra plumbing.
* History entries have no FK-driven deletion on soft removal (removal never deletes the profile row), so they survive it unchanged; a hard delete cascades them away with the rest of the profile.
* No function from an earlier migration is redefined.

## Other admins (manual)

The first admin is automatic (above). To promote someone else:

1. Create an invite with `supabase/seed/first_invite.sql` (SQL editor; the code appears in the result), then sign up at `/join` with it and finish account setup, so the account and its pending profile exist.
2. Copy `supabase/seed/promote_admin.sql` into the Supabase SQL editor, replace the placeholder email there, and run it. Never commit the edited copy.

`20261103120000_retired_status.sql` (MVA-238): Retired status for members who stop playing without being removed.
* `'retired'` is a profile STATUS, not a tier. `profiles` gains `retired_at` and `retired_from_tier` (a plain uuid, deliberately not a foreign key: a second profiles -> tiers relationship would make every `tier:tiers(...)` PostgREST embed ambiguous). The tier itself is left unchanged by retirement.
* Seats, tallies and readiness already count only approved/suspended accounts (`seat_tally`, event readiness, tier breakdown), and `has_capability` needs `approved`, so a retired member frees an Old Guard / Command seat at once and holds no capability. Returning into a full seat is refused by the existing `profiles_seat_cap` trigger.
* Limited access: `traffic_select` and `profiles_select_roster` (both replaced from their newest definitions) also admit retired viewers via the new `current_user_is_retired()`. Everything gated on `approved` (event details, minutes, documents, RSVPs, other members' private rows) stays closed; own profile, own private row, own service record and own notifications are theirs by existing own-row policies.
* `retire_member(profile, reason)` / `unretire_member(profile, tier)`: SECURITY DEFINER, need `edit_roster` (Command; Admin passes), fixed error codes (`not allowed`, `cannot_retire_self`, `not_active`, `not_retired`, `invalid_reason`, `invalid_tier`, `not_found`). Retiring vacates designations and office seats (each logged in `designation_audit`); they are not restored on return. Both write `profile_audit` rows (`retired` / `unretired`: who, when, tier, reason).
* `profiles_guard()` is replaced from `20261013220000_support_tier.sql` with ONE generic bypass: the transaction-local setting `odz.member_rpc` (`retire`, `unretire` or `reinstate`, set only inside the SECURITY DEFINER RPCs) skips the `approve_members` check on a status change, and `reinstate` lets a removed account be brought back (MVA-249). Every other guard rule (own status, admin profiles, last admin, tier entry rules) still applies. Later migrations that redefine the guard must copy this version.
* Additive: one status value, two nullable columns, two audit event names, new functions, two replaced policies, one replaced trigger function. No existing row is rewritten.

`20261103130000_member_reinstate.sql` (MVA-249): reinstate a soft-removed member.
* `reinstate_member(profile, reason)`: Admin-only SECURITY DEFINER, search_path pinned, fixed error codes (`not allowed`, `invalid_reason` for 3 to 500 characters, `not_found` for a hard-deleted account, `not_reinstatable` for anyone not soft-removed, including the caller). It reverses what `remove_member()` did to sign-in: `auth.users.banned_until` (set to now() + 100 years) goes back to null; sessions were deleted at removal, so the member signs in fresh with the same email and password.
* The profile returns `approved` with `removed_at` / `removed_by` cleared and `setup_complete = false` (removal purged `member_private`, so first-login setup runs again). Tier: the previous tier, except Old Guard and Command return as Member (seats come back only through the normal promotion path and the seat caps, never by reinstatement). The call returns the tier name.
* Not restored: designations (cleared and logged in `designation_audit`, because `remove_member()` left the rows in place and they would otherwise go live again), private data, revoked invites. Service history and DOE were never deleted. Past authorship shows the callsign again because the profile row never left.
* Audit: `profile_audit` event `member_reinstated` (who, whom, when, reason in `note`, previous and resulting tier); no private values.
* `profiles_guard()` is replaced from `20261103120000_retired_status.sql` (newest) with one change: under `odz.member_rpc = 'reinstate'` the tier release rule and entry prerequisite are skipped (otherwise a removed Command member returned as Member would be rewritten to Old Guard by `tiers.release_to_tier_id`). Later migrations that redefine the guard must copy this version.
* Additive: one audit event name, one replaced trigger function, one new function. No existing row is rewritten.

`20261103140000_password_change_audit.sql` (MVA-248): change password in the app.
* The change itself is Supabase Auth: the client re-checks the current password with `signInWithPassword` (the member's own email), then calls `updateUser({ password })`, then `signOut({ scope: 'others' })`. No table and no email is involved. This migration only adds the audit trail, because the browser cannot write `profile_audit`.
* `log_password_change()`: SECURITY DEFINER, no arguments, search_path pinned. Approved and retired accounts only (pending, suspended, removed and anon are refused with `not allowed`). It writes one `profile_audit` row for the caller, event `password_changed`, fixed values `password` -> `changed`, no note. No password, partial password or hash is ever passed to or stored by it. The row is self-reported; Supabase Auth stays the source of truth.
* **Dashboard setting: leave Auth > Providers > Email > "Secure password change" OFF** (dev and prod). With it on, Supabase requires a recent sign-in or an email confirmation for a password change, and this feature must work with no email (MVA-200, SMTP, is separate). The client's own re-authentication with the current password is the check that setting would otherwise provide. `supabase/config.toml` leaves it at its default (off) for the local stack.
* Additive: one audit event name and one new function.

`20261103150000_motions.sql` (MVA-233): the Command motion-and-vote engine. Subject features ask for a decision with `open_motion()` and read it back with `motion_result()`.
* `motions` carries both an explicit `state` (draft / open / closed) and a `status` (open / decided / escalated / escalated_final / withdrawn), the linked subject (`subject_type` + `subject_id`), an optional parent record (`parent_type` + `parent_id`, e.g. an agenda item), `options` (default Approve / Reject; a subject can supply its own, 2 to 6) and a deadline (default 72 hours). Eligible voters are snapshotted per round in `motion_voters` when the round starts (the body, minus parties and recused members) and never recomputed on read.
* A strict majority of all eligible voters decides, early if it arrives before the deadline. A tie (or no option able to reach a majority, or the deadline passing without one) or fewer than 3 eligible voters escalates the same motion from round 1 (Command) to round 2 (Old Guard, Command included); a second tie or fewer than 3 ends in `escalated_final`, which only an Admin closes with `decide_motion_final()` and a reason. "Team Lead" is not modelled in the schema, so the final step is the spec's last fallback (an Admin); flagged on the PR.
* Votes are open ballot, by name, changeable until the motion closes. `motion_votes` holds the current choice; every cast and change is also in the append-only `motion_log` (who, when, before/after). Nothing (motion, vote, party, recusal, log row) can be deleted, and the log cannot be edited. Profile columns have no foreign key, so hard-deleting a removed member (MVA-209) cannot erase a recorded vote.
* Clients have SELECT only; every write is a SECURITY DEFINER RPC (`open_motion`, `start_motion`, `cast_vote`, `recuse_from_motion`, `withdraw_motion`, `decide_motion_final`). Visible to Old Guard, Command, Admin and the motion's parties; a draft only to its opener, Command and Admin. Anon has nothing.
* New capability `open_motions` (Command by default; Admin passes every check). Notifications gain the kind `motion`: opened (eligible voters), 24 hours before the deadline (voters who have not voted), result (everyone who can see it). `process_motions()` closes lapsed rounds and sends the reminders; pg_cron runs it every 5 minutes where available, and the Motions page also calls it (it is idempotent), so dev works without cron.
* Redefines nothing. Widens `notifications_kind_check` by one value.

`20261103160000_meeting_agendas.sql` (MVA-245): structured meeting agendas.
* `agendas` (one per event, `event_type = 'Meeting'` only, enforced by a trigger) is a draft until a `write_events` holder calls `publish_agenda()`; publish and republish are logged in the append-only `agenda_publish_log` (who, when) and notify every member who can read event details (new notification kind `agenda`).
* `agenda_items`: title, planned minutes, kind (inform / discuss / vote), optional presenter, notes (markdown, 3,000 characters), `vote_wording` (exact motion text), `outcome_md`, and a visibility level: **members** (default), **command** (Command and Admin) or **presenter** (the named presenter plus Command and Admin). Presenter notes live in their own table, `agenda_item_notes` (Presenter level always), because RLS works on rows, not columns. Drafts are visible only to Command, Admin and `write_events` holders; anon has no grant on any of it.
* Edits after publishing mark the item (`edited_since_publish`); a second `publish_agenda()` re-notifies and stamps those items `updated_in_publish` so members see an "updated" mark. Outcome and order changes do not count as agenda changes.
* `agenda_item_documents` links existing Documents to an item; the document keeps its own RLS, so a link never widens access. `reorder_agenda_items()` re-orders in one call.
* `create_minutes_from_agenda()` (needs `write_minutes` and a manager role) pre-fills a minutes **draft**: headings, vote wording, an outcome line per item, attendees from the RSVPs. Presenter notes and non-Members-level items are copied only when asked.
* The vote-item link to a motion (MVA-233) is not here; MVA-246 adds it once both are on dev. Widens `notifications_kind_check` ('agenda', and 'motion' so either migration order is safe). Redefines nothing.

`20261103170000_live_meeting_votes.sql` (MVA-246): live meeting votes, built on the motion engine (MVA-233) and agenda vote items (MVA-245).
* `open_live_vote(item)` (`write_events`, the chair) turns a vote item of a **published** agenda into a motion with `mode = 'live'`, body Old Guard (Command included), parent = the agenda item, options Yes / No / Abstain, **no deadline**. The motion wording is copied and frozen: `agenda_items_prepare()` refuses to change `kind` or `vote_wording` of an item that has a vote. Eligible voters are snapshotted when voting opens (Old Guard and Command, minus parties and recused members; only approved accounts, so Retired and removed members are out).
* **Choices are hidden until the chair closes** (spec default; open decision for Dax: the alternative is a live tally). While open a voter reads only their own vote and `live_vote_progress()` counts; the vote rows and the vote entries of `motion_log` are closed to everyone else, the chair and Admin included. `close_live_vote()` reveals them. Only the chair closes a live vote; the engine's early close and deadline sweep skip live motions.
* **Result by D27 (spec default):** strict majority of ALL eligible voters. Yes majority = passed, No majority = failed, anything else = tie. A tie, or fewer than 3 eligible voters, waits (`escalated_final`) for an Admin to record the outcome, as in MVA-233. **Quorum** is `meeting_vote_settings.quorum`: **no default (null)**, set by an Admin with `set_vote_quorum()` (logged in `settings_audit`), snapshotted into the motion when it opens; when set, fewer votes cast (abstentions count) = `no_quorum`, which closes the vote with no outcome. Open decision for Dax: whether quorum is a vote count (as built) or a fraction.
* **Consulted members** (`motion_consulted`, `motion_advisory_votes`): by default approved accounts that hold `read_event_details` (Member and above), are not role-based (Support) and are not in the voting body; the chair may pass explicit tiers. The poll is recorded separately, hidden while open, never counted. A consulted member can see the motion (`can_see_motion()` extended).
* `record_vote_for()`: the chair records a vote for a voter who cannot use the app; flagged (`recorded_by`, required `record_note`), shown "recorded by chair", cannot overwrite a voter's own vote, and the voter cannot change it afterwards.
* A closed vote cannot be reopened or edited; a withdrawn one (before any vote) frees the item. `create_minutes_from_agenda()` adds, for each closed live vote: the result, every voter's choice by name, chair-recorded flags and the advisory counts.
* Redefines `can_see_motion()`, `motion_evaluate()`, `cast_vote()` (from `20261103150000_motions.sql`), `agenda_items_prepare()` and `create_minutes_from_agenda()` (from `20261103160000_meeting_agendas.sql`), each copied from its newest definition with the change commented. Replaces the `motion_votes` and `motion_log` SELECT policies. Adds columns to `motions` and `motion_votes`, widens `motion_log_action_check`.
